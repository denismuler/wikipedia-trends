# Wikipedia Trends — Agent Skill для AI Product Engineering School

Практичне завдання курсу **AI Product Engineering School**: навичка (Agent
Skill) для AI-агента, яка допомагає засновникам B2C-продуктів вирішувати,
яку тему розвивати далі та якою мовою запускати продукт, спираючись на
реальну статистику переглядів Wikipedia (Wikimedia Pageviews API).

**Навичка лежить у директорії [`wikipedia-trends/`](wikipedia-trends/)** —
там і `SKILL.md`, і весь код, який виконує змістовну роботу з даними. Цей
кореневий `README.md` — не частина навички, а опис логіки виконання роботи
для перевірки завдання.

## Встановлення skill (Cursor, Claude Code, Claude)

Усі варіанти використовують **ту саму папку** `wikipedia-trends/` (з
`SKILL.md` у корені цієї папки). Python **3.10+** і доступ до
`wikidata.org` / `wikimedia.org` обов’язкові для живих даних.

### Спільна підготовка (один раз на машину або в сесії агента)

```bash
cd wikipedia-trends
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest tests/ -q   # опційно: 17 offline-тестів
```

Перевірка, що API доступний:

```bash
.venv/bin/python scripts/wiki_trends.py run --topic astronomy --langs uk --months 12 --open
```

Після `run` у терміналі з’явиться блок **DELIVERABLES**: графік у чаті
(markdown), копії в **~/Downloads**, опційно Preview через `--open`.

### Cursor

1. **Склонуй або відкрий** цей репозиторій у Cursor (workspace = корінь
   `wikipedia-trends-skill`).
2. **Підключи skill** одним із способів:
   - **Особистий (усі проєкти):** скопіюй каталог `wikipedia-trends` у  
     `~/.cursor/skills/wikipedia-trends/`  
     (усередині має лежати `SKILL.md`, тобто  
     `~/.cursor/skills/wikipedia-trends/SKILL.md`).
   - **Лише цей репо:** скопіюй у  
     `.cursor/skills/wikipedia-trends/` у корені workspace  
     (шлях від git root: `wikipedia-trends-skill/.cursor/skills/wikipedia-trends/`).
3. У чаті з Agent увімкни **виконання команд у терміналі** (якщо вимкнено —
   агент не зможе запустити `wiki_trends.py`).
4. Запитай українською/англійською про тренд Wikipedia, напр.:  
   *«Порівняй інтерес до intermittent fasting у pl і cs за 2 роки»* — агент
   має прочитати skill і виконати `scripts/wiki_trends.py run …` з каталогу
   skill (або з `wikipedia-trends/` у workspace).

**Порада:** якщо skill не підхоплюється, явно напиши: *«використай skill
wikipedia-trends»* або додай у проєкт правило з посиланням на
`wikipedia-trends/SKILL.md`.

### Claude Code (CLI на Mac / Linux)

1. Склонуй репозиторій (або скопіюй лише `wikipedia-trends/`).
2. Встанови skill у каталог skills Claude Code:
   - **Глобально:** `~/.claude/skills/wikipedia-trends/`  
     (файл `~/.claude/skills/wikipedia-trends/SKILL.md`).
   - **У проєкті:** `.claude/skills/wikipedia-trends/` у корені репозиторію,
     з якого запускаєш `claude`.
3. Відкрий термінал у папці skill і зроби `venv` (див. «Спільна підготовка»).
4. Запусти Claude Code у цьому проєкті. У сесії агент бачить skill за
   `description` у frontmatter `SKILL.md`.
5. У командах використовуй шлях до Python skill-директорії, напр.:

   ```bash
   cd /шлях/до/wikipedia-trends
   .venv/bin/python scripts/wiki_trends.py run --topic "…" --langs pl,uk --months 24
   ```

   У документації Claude Code для skills інколи доступна змінна
   `${CLAUDE_SKILL_DIR}` — підстав її замість ручного шляху, якщо вона є в
   твоїй версії CLI.

**Мережа:** локальний термінал зазвичай має повний HTTPS — це найзручніший
спосіб отримати реальні графіки й PDF.

### Claude (claude.ai / Claude Desktop — Skills + code execution)

1. **Збери zip без `.venv` і без симлінків** (готово для завантаження):

   ```bash
   ./scripts/pack-for-claude-ai.sh
   # створює wikipedia-trends-skill-claude-ai.zip у корені репо
   ```

2. У **Claude** → **Settings** → **Capabilities** (або **Customize**):
   - увімкни **Code execution** (виконання коду);
   - увімкни **Network egress** / allowlist доменів: мінімум  
     `wikidata.org`, `wikimedia.org`, `wikipedia.org`  
     (або **All domains**, якщо allowlist незручний).
3. **Settings** → **Skills** → завантаж zip або вкажи папку skill (залежно
   від UI версії).
4. **Почни новий чат** після зміни мережевих налаштувань — стара сесія може
   лишатися в старому sandbox.
5. У новому чаті попроси аналіз тренду; агент має:
   - один раз `pip install -r requirements.txt` у sandbox;
   - запустити `wiki_trends.py run`;
   - показати графік з рядка **Paste in chat (markdown image)** у блоці
     DELIVERABLES.

Якщо `pip` працює, а `run` падає з `403` / blocked host — розширь
allowlist, не відповідай «загальними трендами» без даних (див. `SKILL.md`).

**Обмеження веб-sandbox:** файли з `/Downloads` на твоєму Mac у чат
claude.ai **не з’являться автоматично** — копія в Downloads працює лише при
запуску скрипта **локально** (Cursor / Claude Code). У браузері орієнтуйся на
шляхи з DELIVERABLES у виводі sandbox або завантаження з сесії коду, якщо UI
це дозволяє.

## Логіка виконання

### Чому Wikidata, а не пряме порівняння назв статей

Одна й та сама тема має різну назву в кожній мовній версії Wikipedia
("Intermittent fasting" / "Přerušovaný půst" / "Переривчасте голодування").
Замість того щоб просити користувача або агента вручну підбирати назву
статті під кожну мову, навичка:

1. шукає тему на **Wikidata** (`wbsearchentities`) і отримує канонічний
   `QID` (наприклад `Q1666254`);
2. читає **sitelinks** цього `QID` (`wbgetentities`), щоб отримати точну
   назву статті в кожній потрібній мовній редакції.

Якщо для якоїсь мови немає sitelink — це **не** трактується як "нульовий
інтерес", а явно позначається як "статті не існує" з окремим попередженням
(можливо, тему просто не написали, а не що вона нікому не цікава). Це
принципова відмінність від наївного підходу "перекласти назву й
спробувати запит".

### Чому саме ці статистичні метрики

- **Рік-до-року (YoY)** замість «нахилу лінії» як основний показник —
  бо він гасить сезонність (тема, що завжди зростає у вересні через
  навчальний рік, не має виглядати як «стійке зростання»).
- **Тест Манна-Кендалла** (реалізований напряму на `numpy`/`math.erf`, без
  `scipy`) — щоб відрізнити «є статистично значуща тенденція» від «це просто
  шум за 3-4 випадкові місяці». Кожна оцінка довіри супроводжується
  конкретним p-value, а не інтуїцією.
- **Виявлення спайків** (>3× медіани попередніх 6 місяців) і перерахунок
  тренду без них — щоб відрізнити вірусну новину від стійкого зростання
  інтересу. Якщо напрямок тренду змінюється після видалення спайку — це
  явне попередження в звіті.
- **Рейтинг довіри (low/medium/high)** — прозора адитивна оцінка (довжина
  історії, обсяг переглядів, значущість тренду, варіативність, згода
  тренду зі/без спайків). Кожна складова одразу перетворюється на
  людське речення-застереження, а не залишається «чорною скринькою».

### Чому єдина CLI-команда, а не «агент сам пише код щоразу»

Вимога завдання явно каже: «Одного Markdown-файлу або інструкцій агенту
щоразу самостійно написати потрібний код недостатньо». Тому вся змістовна
робота — HTTP-запити, кешування, статистика, побудова графіків і PDF —
живе в протестованому Python-коді (`scripts/`), а `SKILL.md` лише каже
агенту, **яку команду запустити й що зробити з результатом**. Це критично
для дешевої/швидкої моделі: вона не повинна вигадувати формули регресії чи
парсити JSON вручну — вона читає готовий, вже сформульований людською
мовою підсумок у stdout.

### Як навичка допомагає агенту оцінювати результати й перевіряти висновки

- Кожен запуск друкує **resolved Wikidata item** (id + опис) з явним
  нагадуванням «VERIFY» — агент має звірити, що тема розпізналася
  правильно, перш ніж довіряти числам (а не мовчки продовжувати, якщо
  "Mercury" розпізналося як планета, а мова була про хімічний елемент).
- Кожен ряд має **явний `confidence` + список `caveats`**, тож агент
  ретранслює вже сформульовані застереження, а не сам оцінює «наскільки
  цим можна довіряти».
- Методологічна примітка («перегляди ≠ готовність платити») зашита прямо
  в `SKILL.md`, щоб агент завжди озвучував це припущення користувачу.
- Функція `rank_series` перетворює набір проаналізованих рядів на
  **готову ранжовану рекомендацію** «що дослідити далі» з обґрунтуванням
  на конкретних числах — саме те, що просить приклад №3 із умови завдання.

### Як навичка ефективно виконує повторні й пов'язані запити

- Усі відповіді Wikidata (30 днів) і Pageviews API (7 днів) **кешуються**
  на диск за ключем (мова, стаття, точний діапазон дат). Уточнення
  запиту («а додай ще українську», «а що там з наступним місяцем») не
  повторно тягне вже отримані дані.
- Єдиний CLI має підкоманди `resolve` / `fetch` / `analyze` / `run` —
  агент може повторити лише той крок, що змінився (наприклад, лише
  `run --qid ...` з правильним ідентифікатором, якщо тему розпізнало
  неправильно), замість переробляти весь пайплайн.
- `--articles "lang:Точна назва,..."` дозволяє одразу пропустити крок
  розпізнавання, якщо агент/користувач вже знає точні назви статей.

## Як розвивати навичку далі (roadmap)

**Фаза 2 — глибші дослідження на тому ж масштабі:**
- автопошук суміжних тем через Wikidata (властивості "subclass of" /
  SPARQL-запити на пов'язані сутності), щоб агент сам пропонував «а ще
  варто перевірити X» без того, щоб користувач називав кожну тему вручну;
- незалежна крос-перевірка сигналу (напр. Google Trends через `pytrends`)
  — щоб «high confidence» означало не лише «стабільно за даними
  Wikipedia», а й «підтверджено іншим джерелом»;
- сезонна декомпозиція (STL) замість простого YoY для сильно сезонних тем;
- bootstrap-довірчі інтервали навколо % росту замість лише p-value.

**Фаза 3 — більші обсяги даних:**
- перехід кешу з окремих JSON-файлів на SQLite/DuckDB зі схемою
  (проєкт, стаття, місяць, перегляди) — зараз кеш прив'язаний до точного
  діапазону дат, тож зміна вікна на «останні 3 роки» замість «2 роки» не
  повністю перевикористовує вже завантажені місяці; таблична схема це
  вирішує без зміни зовнішнього API навички;
- пакетний/паралельний фетч (`asyncio`/пул потоків) із загальним
  rate-limiter'ом для запитів на десятки тем × мов одночасно;
- підтримка масових дампів Wikimedia (pageviews dumps) для
  дослідження тисяч статей одразу, коли REST API «по одній статті» стає
  завузьким горлом.

**Фаза 4 — продуктова ергономіка:**
- багатосторінковий/HTML-звіт, коли тем/мов більше трьох (зараз
  одна сторінка розрахована на компактне порівняння 2–4 рядів);
- GitHub Actions: unit-тести + «дим-тест» одного реального запиту на
  кожен push, щоб одразу помітити зміну форми відповіді Wikimedia API;
- легкий локальний журнал запитів (тема → confidence → дата), щоб
  на повторне «а що ми вже перевіряли цього кварталу» агент відповідав
  без повторного виклику API.

## Як тестувалося (і як я перевіряв AI-інструменти)

Навичка розроблялася в Cursor з активним використанням AI-агента
(Claude) як пар-програміста — від дизайну архітектури (Wikidata-резолюція,
вибір статистичних тестів, формат CLI) до написання коду й документації.
Перевірка результату відбувалася на трьох рівнях, а не «на слово»:

1. **Unit-тести** (`tests/test_trend_analysis.py`, 17 тестів, без мережі) —
   перевіряють чисту статистику на синтетичних рядах з відомою відповіддю
   (наприклад: ряд із точним компаундним ростом 10%/міс → `monthly_pct`
   має бути ≈10.0; ряд без тренду → Mann-Kendall не має видати
   `increasing`/`decreasing` зі значущим p). Усі 17 проходять.
2. **Живі прогони на реальному Wikimedia API** для всіх трьох прикладів з
   умови завдання — результати (числа, графіки, PDF) закомічені в
   `wikipedia-trends/examples_output/` і задокументовані в `examples.md`,
   щоб перевіряючий міг звірити код із фактичним, а не гіпотетичним,
   виводом.
3. **Наскрізний тест на дешевій/швидкій моделі**, як вимагає завдання: я
   запустив увесь сценарій через окремого AI-субагента на **Gemini 2.5
   Flash** (клас моделі, аналогічний Claude Haiku 4.5 — швидка, дешева,
   з підтримкою інструментів), давши йому **лише** шлях до директорії
   навички й те саме питання з умови завдання українською, без жодних
   підказок понад те, що написано в `SKILL.md`. Результат: модель
   самостійно прочитала `SKILL.md`, виконала одноразовий setup
   (`venv` + `pip install`), запустила `wiki_trends.py run` з правильними
   параметрами і **за 3 виклики інструментів** (Read + 2×Shell) видала
   коректну, обґрунтовану відповідь з правильними числами, рейтингом
   довіри та застереженнями — і сама відзначила, що `SKILL.md` було
   достатньо, без потреби читати `reference.md`/`examples.md`. Це і є
   практична перевірка «навичкою зручно й ефективно користуватися на
   швидкій недорогій моделі» з вимог завдання, а не просто твердження.

## Припущення й обмеження (винесені й у `reference.md`)

- Перегляди Wikipedia — сигнал *інтересу/уваги*, а не готовності платити;
  використовується як привід для подальшої перевірки, не як остаточне
  рішення.
- Дані per-article доступні від 2015-07; запит із раннішою датою
  автоматично обрізається.
- `agent=user` виключає ботів/сканери, але не виключає, наприклад, масові
  переходи з новинного посилання (для цього є окреме виявлення спайків).
- Розпізнавання теми на Wikidata бере перший (найкращий) збіг пошуку —
  для двозначних тем агент має звіряти `qid`/опис перед тим, як довіряти
  числам (саме тому це друкується першим рядком у виводі `run`).
